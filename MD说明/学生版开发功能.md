# 学生版开发功能：记录功能规划

本文记录开发方案及 v2 实施结果。录音、录像、拍照已接入新的学生控制链；学生端不再划分实验种类，不保留实验选择流程。

启动后助手待命。用户表达纠错需求 → Qwen 保留具体检查要求 → 拍照 → Gemini 提取可见事实和检索词 → 查知识库 → Gemini 结合原照片、用户要求与资料给出建议。接口使用 `general_check`，附带 `check_request`，不传实验分类，不调用旧 CV／参考图流程。没有资料时明确说明仅依据照片判断。旧流程代码保留供旧入口使用。当前模型为七牛云 `google/gemini-3.5-flash`。记录上传中的 `unknown_experiment` 仅用于兼容旧存储字段。

最终结构：持续收音 → 一段语句上传 → AI 返回固定动作或 `no_action` → 程序检查状态并执行。新版学生链已取消 `unclear`、追问和单独唤醒步骤；不确定就保持安静，由用户重新表达。教师版及旧 APK 的后端上下文继续兼容。

## v2 实施结果与使用

- 眼镜端由 `StudentAudioCapture` 负责一路 16kHz 麦克风；语音结束后约 0.7 秒提交一段，长语句最多 8 秒分段，等待网络／模型期间采集不停止。
- 决策请求串行发送，最多保留 4 段待处理语句；拥塞超过这个上限会丢弃最旧的待判定片段，正式记录继续保存。状态变化或退出会丢弃旧决定，避免旧请求干扰新记录。
- `student_*` 后端上下文一次映射固定动作，没有转写关键词兜底自动执行；未知／缺失／非法动作全部 `no_action`。问答直接使用本次问题。
- 记录状态在 `RecordingService` 独立管理。声音原件采用 WAV，约 1.9 MB／分钟；录像使用 CameraX 画面与同一路音频，结束后通过系统编码器合成为有声 MP4。合成失败保留音视频原件并明确标识音轨分开，不删除原件。
- 录音能补入已识别的请求语句及短期缓冲中的后续声音；可能包含口令，不自动剪删。录像从相机真正开始时保存，不追溯之前画面。
- 照片和记录保存到应用持久目录，上传清单保留并每 30 秒重试；只在收到有效上传回执后清理本地媒体。新版后端按稳定客户端 ID 去重，重复上传不覆盖原件。
- 本轮语音分段、动作解析、重复上传测试通过；眼镜上验证了关闭指令判定时仍持续保存录音，以及最终 MP4 同时含音视频轨道。真实自然语言、误触率、长时间录制及音画主观同步效果还需佩戴验证。
- 本地 Docker 用一组生成语音验证了“开始录音 → 老师问候及蒸馏水陈述 → 保存录音”，依次返回 `start_audio_recording`、`no_action`、`stop_recording`。临时眼镜自动测试代码已删除，只保留简短基础测试。
- 持续采集指 App 使用期间；退出／进入后台会结束正在进行的记录并保存，不是全天后台录音。未发出记录请求时只有短期监听数据，不产生正式实验记录。

构建普通学生版：`./gradlew.bat :app:assembleStudentDebug`。构建独立 USB 测试包：`./gradlew.bat -PstudentTest :app:assembleStudentDebug`，包名 `com.example.zrgfirstapp.naturaltest`，应用名“学生自然语音测试”，可与原学生版共存。

新 APK 必须配套更新后端，健康接口需包含 `student_direct_control`。旧服务器会显示需更新后端，避免新 APK 使用旧的分类协议。2026-10-16 已部署至 `.134`，知识库已启用；语音意图、知识库问答及双份整理的实际调用验证通过。眼镜 APK 需要单独安装，USB 包仍访问本机转发。

本地 Docker 测试使用 `http://127.0.0.1:5081`；USB 连接后运行 `adb reverse tcp:5080 tcp:5081`，测试包访问的眼镜 `127.0.0.1:5080` 即转到本机 Docker。也可启动本机 Python 后端 5080，再使用 `adb reverse tcp:5080 tcp:5080`。

## 1. 基本目标

学生版持续监听，模型判断学生是否在向小北提出需求。用户主动要求录音、录像或拍照时，才保存相应的正式实验资料。

监听与保存分开：

- 监听音频只作为短期意图判断输入，使用有限的内存缓冲或临时文件，不自动成为实验记录。
- 录音、录像是由用户明确开始、明确结束的一段记录；拍照是一次性记录。
- 使用云端模型判断时仍会发送监听语音片段；“不保存为实验记录”不等于音频没有被处理或传输。
- 录制期间的普通实验谈话继续进入用户主动开启的记录，但不会因为被模型听到而自动执行动作。

## 2. 三个功能和自然语言含义

| 功能 | 示例 | 执行含义 |
|---|---|---|
| 开始录音 | “小北，开始录音”“小北小北，把我说的录下来”“帮我记录一下” | 开始保存声音；泛称“记录”默认录音 |
| 开始录像 | “小北，把现在这个实验过程拍成视频”“开始录像” | 开始保存视频及声音；需要明确的视频需求 |
| 拍照 | “小北，拍张照片”“帮我把现在这个画面拍下来” | 保存一张照片，不自动分析或开始录像 |
| 结束记录 | “小北，停止录音”“把这段录像保存下来”“录好了，结束记录” | 结束当前录音或录像，先保存在眼镜上，再上传 |

“小北助手”“小北小北”等称呼作为对话对象的线索，不要求先单独唤醒、等待回应，再重复说需求。“小北，开始录像”应在一次判断中返回动作。

“记录”默认录音，明确要画面／视频才录像；如果结合上下文仍无法理解需求，返回 `no_action`，不追问。

## 3. 一次映射到固定动作

每次给模型：本次语音、当前记录状态、最近的简短对话、当前可执行动作。模型在一次请求中判断交谈对象及需求，直接返回一个固定 `intent`：

| intent | 行为 |
|---|---|
| `no_action` | 静默继续监听：无关内容、对象不明确、听不清、需求不清楚或不支持 |
| `start_audio_recording` | 开始录音 |
| `start_video_recording` | 开始录像 |
| `stop_recording` | 结束当前记录并保存 |
| `capture_photo` | 拍照保存 |
| `qa` | 用本次语句的问题进行回答，不要求重复录问题 |
| `experiment_check` | 检查实验装置／操作 |
| `safety_check` | 检查安全 |
| `demo_guide` | 进入现有演示视频流程 |

不再增加独立的 `ignore`、`execute`、`clarify` 或 `address_only` 决定层。未知、缺失或非法 intent 统一降为 `no_action`。只有称呼、没有明确需求时也保持安静。`no_action` 不播报、不显示识别失败、不追问，也不改变当前记录状态。明确任务的成功／失败通知属于执行结果，不属于自由追问。

`qa` 可回答用户的问题，但不能借回答自行执行记录等动作。视频选择和停止等已有流程仍使用各自允许的固定动作。第一阶段仅实现记录动作与 `no_action`；其余动作沿用现有入口，逐项接入。

| 场景 | 例子 | 控制行为 |
|---|---|---|
| 普通实验陈述 | “我要加点蒸馏水” | 忽略；若正在录制，作为录制内容保留 |
| 对别人讲话 | “郑老师好”“你帮我拍一下吧，张同学” | 忽略 |
| 明确请求小北 | “小北，帮我记录这段话” | 开始录音 |
| 不明确的结束语 | “可以了”“差不多了” | 不单独作为停止记录依据；结合最近的助手对话，否则忽略 |
| 停止实验操作 | “先停加热”“停止滴加” | 不停止录音或录像 |
| 紧接上一项请求 | 小北刚确认保存录音，学生说“再开始录像” | 结合最近的助手对话执行，不需要追问 |

最近对话只作为模型判断的上下文，不单独设置一个必须先通过的唤醒关卡。助手回应完成后保留约 10 秒的连续交谈线索；普通师生讨论和 `no_action` 不延长窗口。超时后重新使用“小北”等称呼有助于判断对象，窗口结束不会停止记录。后台较晚返回的旧结果不能停止或重复启动新的记录。

## 4. 记录状态要独立于界面和对话

记录状态建议固定为：`IDLE`（未记录）、`STARTING_AUDIO`、`STARTING_VIDEO`、`AUDIO_RECORDING`、`VIDEO_RECORDING`、`STOPPING`（正在完成文件）。

上传状态另外管理：待上传、上传中、成功、失败待重试。照片作为一次性任务管理，不用“拍照中”覆盖当前录音状态。

| 当前状态 | 收到请求 | 行为 |
|---|---|---|
| 未记录 | 开始录音／录像 | 申请必要权限，启动硬件；成功后才提示“开始录音／录像” |
| 已在录音 | 再次开始录音 | 继续现有记录，不新建第二份 |
| 已在录像 | 再次开始录像 | 继续现有记录，不新建第二份 |
| 已在录音／录像 | 明确停止当前记录 | 完成文件，提示“已保存在眼镜上”，后台上传 |
| 未记录 | 停止记录 | 说明当前没有记录，不创建空文件 |
| 正在启动或完成文件 | 相同请求重复到达 | 合并请求，只执行一次 |
| 录音中要求录像，或录像中要求录音 | 明确切换请求 | 第一版先说明需结束当前记录，不静默截断或自动切换 |
| 未记录或录音中 | 拍照 | 保存照片，录音继续；需实机确认相机初始化不影响麦克风 |
| 录像中 | 拍照 | 仅在验证 CameraX 能同时拍照且不重绑录像后开放；否则明确说明暂不支持，不偷偷结束录像 |

第一版不增加暂停／继续、自动删除和多段合并。未支持或无法理解的需求返回 `no_action`；已识别的任务若受当前状态或硬件限制，可给出简短失败通知，不追问。

## 5. 麦克风只采集一路，同时供监听与正式记录使用

现有学生版通过 `AudioRecord` 采集指令，通过 `MediaRecorder` 保存录音；CameraX 录像也可能打开麦克风。因此持续监听和记录不应只靠换 prompt 实现，要先解决录制期间的收音共用。

建议由独立的音频组件持续采集一路音频：

1. 短期缓冲供语音意图判断；上传和等待模型期间采集继续，避免漏掉停止请求。
2. 用户开启录音后，把同一路数据写入正式文件；停止保存后，意图监听继续。
3. 用户开启录像时，CameraX 先录画面，同一路音频单独保存；用同一记录 ID、时间基准关联。音画同步和结束边界需实机验证。
4. 先允许服务器保存关联的视频和音频；若网页需要直接播放有声音的视频，再增加合并音轨步骤，不把无声 MP4 当成完整有声录像交付。
5. 助手自身播放提示音时，控制判定暂停或过滤回声，不能将提示音识别为学生指令；正式记录不因此被截断。必要时用短提示音减少污染。

教师版已有单路音频及环形缓冲思路，可借鉴结构，但学生版只在用户要求后保存，不复制教师版全程保存的策略。

## 6. 保存边界和结果提示

- 开始时间以音频／视频真正启动的时间为准；权限拒绝或启动失败必须说明失败，不能只把界面改成“录制中”。
- “小北，记录一下：溶液已经变蓝”这类同句带内容的需求，录音应能保留已识别的这段请求语音：待模型确认后，从短期缓冲补入该语句及其后的连续音频，不丢掉前半句话，也不无限回填此前闲聊。
- 补入音频应记录来源时间和边界。第一版可包含开始指令本身，不声称已经精确剪掉口令。录像不承诺追溯拍摄启动前的画面。
- 停止判断存在模型延迟，原始文件可能包含结束指令。记录停止请求时间和实际完成时间，第一版不自动剪删原始素材。
- 停止先完成眼镜上的文件，再异步上传。区分“已保存在眼镜上”和“已上传成功”，上传慢或失败不影响下一次记录。
- 正式文件及待上传清单放在应用持久目录，不只放容易清理的缓存目录；上传成功并确认服务器记录后才允许清理本地副本。
- 网络中断时保留文件并重试；云端意图不可用时通过已有按钮入口开始／结束记录。第一版不把离线语音控制当作已经支持。
- 退出 App 时先完成已开启的记录，不默认丢弃。异常中断的文件恢复能力须按实际编码格式验证，不能承诺所有崩溃都能恢复。

## 7. 后端尽量沿用现有接口

目前已有：

- `/api/glasses/records/upload`：学生录音／录像上传，同次请求可带 `audio` 和 `video`。
- `/api/glasses/photos/upload`：学生照片上传。
- 原始记录、转写／描述、教学派生结果已经分开存储；录音／录像原件不被转写或总结覆盖。

客户端需补充稳定的记录会话 ID、分段 ID、类型、实际起止时间和结束原因；服务器需支持按这些 ID 去重。当前服务器每次上传生成新记录 ID，重试可能形成重复记录，这项尚需实现。

保存原件和上传队列先做好，再做转写和记录检索。单独保存的视频与音轨必须在一条记录中关联；不能把同一次录像的音视频拆成无关记录。

## 8. 实施与验收顺序

1. 先整理记录状态，验证按钮开始／结束录音、录像、拍照；状态以硬件结果为准。
2. 建立共用音频采集和短期缓冲，验证录制过程中停止指令仍能被听到，以及同句内容不丢失。
3. 改模型返回结构，一次完成固定动作映射；取消学生版 `unclear`，无关或不确定语句统一 `no_action` 并静默继续监听，缩小停止请求误判。
4. 建立持久保存、上传队列和后端去重，检查断网后重试、重启后补传。
5. 真机验收：连续两次“开始录音”只生成一段；闲聊不会开始或停止；“停止加热”不会结束记录；明确结束能保存；录像音画对应；拍照不会意外中断记录；上传失败仍可找到原始文件。

实验纠错、问答、视频播放后续复用对话对象判断和固定动作入口，但不由它们随意改动正在进行的记录。是否引入数据库由检索、历史对话和视频目录需求决定，不作为记录功能开始开发的前置条件。
